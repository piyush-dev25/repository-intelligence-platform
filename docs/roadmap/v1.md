# Repository Intelligence Platform — v1 Roadmap

*Locked on 1 Nov 2026 after the regroup. This is the reference for all future work. Change it deliberately, not mid-build.*

## What v1 is
A user uploads a public GitHub repo or a zip. They get a repo dashboard with a summary, metadata and an interactive dependency graph, plus a chat that answers architecture, search, dependency and impact questions with file and line citations. It is deployed with pre-analyzed demo repos.

Framing: a resume and learning project, not a startup or a ChatGPT/Claude competitor. Feasible-but-slow features go to v2.

## Already built (Phases 1–4.5)
- JWT auth (signup/login).
- Repo registration, zip upload, git clone (shallow), delete.
- Filesystem scan: file list, language breakdown, key files, totals, content hashes.
- Tree-sitter extractors for Python, JS, TS, TSX, HTML and CSS, with tests.
- LLM file summaries (Groq), chunked for large files, with retry and backoff.
- Repo-level summary.
- Skipping unchanged files on re-scan, using content hashes.
- Frontend: only a scaffold with a health-check page.

## How we build
- Each roadmap bullet is discussed and designed in the Claude chat first. That chat then produces a detailed prompt for Claude Code.
- Claude Code runs in plan mode. Piyush reviews the plan, checks it in the chat, and approves it before any code is written.
- Claude Code never runs git commands. Piyush does all version control.
- After every change, Claude Code stops and gives a plain-language summary: what changed, how to test it manually, what to watch out for, and the concepts used. Piyush tests manually before moving on.
- Rule for bugs: AI writes the code, but when something breaks, Piyush diagnoses first.
- Study the concepts along the way. Hand-coding reps happen separately in the coding assignments.
- Rules for Claude Code live in `CLAUDE.md` at the repo root. This roadmap lives at `docs/roadmap-v1.md`.

## Locked decisions

### Pipeline
- Saving the zip and cloning the repo happen inside the request. Scanning and analysis run in FastAPI BackgroundTasks, with their own DB session. The frontend polls a status endpoint.
- Duplicate-run guard: while a repo is scanning or analyzing, upload, clone, scan, analyze and delete return 409.
- On server startup, repos stuck in scanning or analyzing are marked failed ("interrupted").
- Analysis is split into passes: structure (Tree-sitter, no LLM) → dependency graph → LLM summaries → embeddings. The graph never depends on the LLM quota.
- Hitting the quota sets a visible "paused" status (today `DailyLimitReached` still marks the repo `ANALYZED`, which must change). Live per-file progress counts are added with the pass split.
- No numeric repo-size cap for now. An honest small-scale note instead. Real limits come after deploy.

### Dependency graph
- Extractors output structured imports (module, names, relative flag) instead of raw strings. All 6 extractors and their tests get updated.
- Storage: a Postgres edges table (source file → target file, or an external package name, plus the raw import text). Deletes cascade.
- Resolution in v1: Python relative and in-repo absolute imports; JS/TS relative imports with extension and `index.*` guessing; TS `@/` aliases via tsconfig paths; HTML `script`/`link` and CSS `@import`; everything unresolved becomes an external node.
- File-level only. Function-level calls are v2.
- Graph endpoint: one endpoint returns all nodes and edges for a repo; the frontend filters.

### Embeddings
- Gemini embeddings, stored in Qdrant.
- One shared collection, filtered by a `repo_id` payload.
- Both file summaries and code chunks are embedded.
- Chunks are functions and methods; classes embed only their header (signature and docstring); small entity-less files become one chunk, while large ones rely on their summary; there is a size limit.
- Chunk text, file path, line range, name and kind are stored in the Qdrant payload, so raw repo files are not needed after processing.
- Re-scans and deletes remove old vectors.

### Query pipeline
- One classifier LLM call (reading the last few messages) returns JSON with the intent, the target files and a standalone rewritten question.
- 5 intents, each with its own context recipe:
  - Architecture: repo summary, metadata and relevant file summaries.
  - Search: code-chunk search.
  - Dependency: graph lookup in both directions.
  - Impact: reverse graph traversal 2–3 levels deep, plus summaries.
  - General: a mix.
- If no file is named, search first to find the target.
- Answers must cite file paths and line ranges, taken only from the provided context.
- Responses stream. The frontend uses `fetch` streaming, not `EventSource`, because of the Bearer auth header.

### Chat
- One thread per repo in the UI, with a "clear chat" button.
- A `chat_sessions` table from day one (one session per repo), so multi-chat in v2 needs only UI work.

### Frontend
- The token lives in localStorage and is sent as a Bearer header. Token expiry is extended (currently 30 minutes with no refresh).
- shadcn/ui for basic pieces (buttons, inputs, dialogs, toasts); the chat window and repo dashboard are hand-built.
- Markdown and code highlighting in chat answers.
- Dependency graph in v1, using React Flow with dagre:
  - Shows the full in-repo graph, with externals hidden and nodes colored by folder.
  - Clicking a file highlights what it depends on and what depends on it.
  - Bigger repos start in focus mode.

## Phases

### Phase 5: Pipeline refactor and dependency graph
- [x] 5.1 Background tasks, duplicate-run guard, startup reset, status endpoint.
- [x] 5.2 Split analysis into passes; quota-paused status; live progress counts; make `summary` nullable.
- [x] 5.3 Structured imports in all 6 extractors, with updated tests.
- [ ] 5.4 Edges table and import resolver, with unit tests per case.
- [ ] 5.5 Graph endpoint.

**Done when:** your own repo processes in the background, the edges are correct, the graph endpoint returns them, and a quota hit shows "paused."

### Phase 6: Embeddings
- [ ] Embedding service, Qdrant collection, entity-based chunking, summary vectors.
- [ ] Re-scan and delete cleanup.

**Done when:** a search on a test repo returns the right chunks with file paths and line numbers.

### Phase 7: Query pipeline and chat backend
- [ ] Classifier call, 5 context recipes, citation-based answer prompt, streaming endpoint.
- [ ] Chat tables, saving messages after each stream, clear chat, longer token expiry.

**Done when:** example questions for all 5 intents, plus a follow-up, get sensible streamed answers with citations through the API.

### Phase 8: Frontend
- [ ] Landing page, login and signup, dashboard, adding a repo by URL or zip with a status display.
- [ ] Repo dashboard: summary, metadata, React Flow graph.
- [ ] Chat workspace: streaming, markdown and code highlighting, citation chips, suggested questions.
- [ ] Deleting and re-analyzing repos.

**Done when:** the full user journey works locally from start to finish.

### Phase 9: Deploy
- [ ] Hosting, a raw-file deletion policy, 2–3 seeded demo repos, the small-scale note, and the fix-before-deploy items.

**Done when:** the live URL works and a recruiter can try a demo repo in under a minute.

## Still open (decide at the phase noted)

- The repo size at which the graph switches to focus mode: Phase 8.
- Using two LLM models (small for summaries and the classifier, large for answers) and sending less per file (summaries from extracted structure instead of raw code). Discussed but not decided. Decide before Phase 7, or sooner if the quota becomes a problem.
- A craft core: which pieces, if any, Piyush builds by hand. Candidates are the import resolver and the classifier with its context recipes.
- A test database setup for service-level tests. Decide before Phase 7.
- Deadline: set by Piyush.

## Fix before deploy
- Chat on partly analyzed repos: block it, or allow it with a warning.
- A per-user rate limit on chat, so one visitor can't use up the daily quota.
- `requirements.txt` includes `pywin32`, which is Windows-only and will fail on a Linux server. The file is also saved as UTF-16; re-save it as UTF-8.
